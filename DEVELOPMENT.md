# Development Guide

How to build, run and test the project, and how the code is organised.

## Overview

Real-time telemetry extraction from SpaceX Starship livestreams. A Python/FastAPI backend grabs video frames, runs OpenCV engine detection and EasyOCR text extraction, and broadcasts structured records over WebSocket to a TypeScript/Chart.js dashboard (Vite, no framework).

## Commands

Setup and launch scripts live in `scripts/windows/` (`.ps1`/`.bat`) and `scripts/unix/` (`.sh`). `setup` creates the venv and installs dependencies, and it auto-selects a CUDA or CPU torch build (override with `TORCH_CUDA`). `start` runs setup and then launches both services.

```bash
# Backend (from backend/, venv activated). Use ".[dev]" for pytest/hypothesis/httpx.
pip install -e ".[dev]"
uvicorn src.server:app --reload          # http://127.0.0.1:8000
pytest                                    # all tests (asyncio_mode=auto)
pytest tests/test_reorder_buffer.py       # one file
pytest tests/test_server.py -k name       # one test

# Frontend (from frontend/)
npm run dev                               # http://localhost:5173, proxies /ws and /api to :8000
npm run build                             # tsc && vite build (type-check gate)
npm test                                  # vitest run
npx vitest run src/core/met.test.ts       # one file
```

No linter is configured for either side. Backend imports use the `src.` package prefix (e.g. `from src.core.models import ...`), so run everything from `backend/`.

**Versioning**: `VERSION` (repo root) holds the SemVer release, `MAJOR.MINOR.PATCH`. The full version adds the commit count (`git rev-list --count HEAD`) as a fourth, build number, e.g. `0.1.0.64`. It is computed by `backend/src/core/version.py` (FastAPI) and by `frontend/vite.config.ts` at build time (`__APP_VERSION__`, shown in the dashboard header). Bump with `python scripts/bump_version.py patch|minor|major|X.Y.Z`, which also updates the copies in `frontend/package.json` and `backend/pyproject.toml`; `tests/test_version.py` fails if they drift.

`results_previous/` is tracked with Git LFS. Without `git lfs install`/`git lfs pull` it contains pointer stubs, not real data.

**Test videos**: downloaded broadcast streams live in `test_videos/<flight>/` (`output.m3u8` plus `seg_*.ts`), e.g. `ift-12/` and `ift-13/`. The folder is local-only: it is excluded through `.git/info/exclude`, not `.gitignore`, so each checkout has to fetch its own copy. The IFT-12 and IFT-13 streams are trimmed to start about 30 s before T-0. Serve one with `python scripts/serve_test_videos.py ift-12` and point the pipeline at `http://localhost:8001/output.m3u8`; without a flight argument every flight is served at `http://localhost:8001/<flight>/output.m3u8`. `--port`, `--host` and `--dir` override the defaults, and the server sends HLS MIME types and `Access-Control-Allow-Origin: *`.

## Architecture

**Backend pipeline** (`backend/src/`): `capture/` (frame extraction) → `vision/engine_analyzer` (Hough circles, colour classification against SVG-derived ROI templates) and `ocr/` (EasyOCR on defined regions) → `telemetry/stage_assignment` (attributes values to Starship or Super Heavy by separation state) → `telemetry/record_assembler` → `core/telemetry_record`, then a WebSocket broadcast from `api/`. `pipeline/` drives the stages and `api/` serves the results.

The packages are layered, lowest first: `core` → `templates` → `vision`, `ocr`, `capture` (peers) → `telemetry` → `storage` → `pipeline` → `api` → `server`. A module may import only from its own package or a lower layer, and peers may not import each other; `tests/test_layering.py` parses every module under `src/` (imports inside functions included) and fails on any other import. The packages' `__init__.py` files import nothing, except `capture`, `ocr` and `pipeline`, which re-export their public API (`ocr` only its result types, so it never loads torch or EasyOCR; `pipeline` lazily, on first access, so importing a submodule such as `src.pipeline.state` does not load the orchestrator either).

- `core/` holds the shared types and plumbing: `enums` (`PipelineStatus`, `SeparationState`, `OCRFieldStatus`), `models` (ROI dataclasses from SVG parsing), `gpu` (`AccelerationBackend`, `GPUCapabilities`), `telemetry_record` (`TelemetryRecord`), `version`, `paths` (`REPO_ROOT`, from which every repo directory such as `missions/`, `diagrams/` or `frontend/dist` is located) and `logging_config`/`logging_context` (human-readable, uvicorn-style logging, with the frame sequence number carried in a contextvar).
- `templates/` builds the ROI templates: `svg_parser` reads the SVGs in `diagrams/` and `template_registry` keeps them by name and loads the default.
- `vision/` holds `engine_analyzer` (engine status from the engine ROIs) and `gpu_detector` (`detect_gpu()`: CUDA or CPU for EasyOCR, reported in the pipeline status; torch is imported only when it runs).
- `ocr/` is the OCR package; `from src.ocr.results import OCRFieldResult, OCRResult` is what the later stages use, and the engine is imported explicitly from `src.ocr.engine`. `engine.py` (`EasyOCREngine`, `configure_torch_threads`) gates on T-0 and reads each frame's ROIs, using `parsing.py` (field kinds, allowlists, time/number/unit parsers), `regions.py` (ROI clamping and cropping, grayscale, narrowing value boxes to their text) and `cache.py` (`FieldCache`: static ROIs such as units and stage labels are reused while their pixel signature is unchanged, and re-read at least every `CACHE_REFRESH_FRAMES` frames). The rest go to `batcher.py` (`BatchedRecognizer`), one recogniser pass over the ROIs of every frame in flight. On GPU that pass is `mixed.py`, a step-for-step copy of EasyOCR's `get_text` with a per-crop allowlist mask, so it depends on EasyOCR internals (pinned `<2.0`).
- `capture/` is the frame capture package; `from src.capture import FrameExtractor, FrameExtractorConfig, SourceUnavailable` is its public API. `extractor.py` (`FrameExtractor`) runs the capture loop (open the source, read the next kept frame, dispatch it, recover a lost source) on top of two base classes: `notifier.py` (status and frame callbacks) and `connection.py` (the main capture handle: locked reads, seeking, release and reconnection with backoff). `config.py` holds the config, tuning constants and `SourceUnavailable`, `source.py` all OpenCV access and `reconnect.py` the retry with exponential backoff. A seekable file is decoded with `parallel_decoder.py` (several decoders over separate stretches, same frames as serial decoding) when `planning.py` finds the skip interval long enough to pay for the seeks; live streams are read serially.
- `telemetry/` turns one frame's results into a record: `stage_assignment` (`StageAssigner`, stateful, so it runs in video order) and `record_assembler`.
- `storage/` holds the file-backed data the API serves, all located from `core.paths`: `previous_flights` (`results_previous/`), `trajectories` (`trajectories/positions_ship<N>.csv`, below-ground rows and repeated polls dropped) and `missions` (one JSON file per mission in `missions/`).
- `pipeline/` is the orchestration package; `from src.pipeline import PipelineOrchestrator, PipelineState` is its public API. `orchestrator.py` handles Start/Stop, dispatches each captured frame (inline before T-0, as a bounded concurrent task after it) and owns the collaborators: `frame_processor.py` (`FrameProcessor`: OCR engine, ROI config, thread pools, T-0 flag, the per-frame stages and record assembly), `ordering.py` (`ReorderCoordinator`: reorder buffer, stale-gap and overflow handling, stage assignment in video order, broadcast sequence and FPS) and `broadcast.py` (`Broadcaster`: the ordered send queue and its worker, which appends each `telemetry` record to the history right before broadcasting it). `history.py` (`TelemetryHistory`) keeps the current Run's records (a Run lasts from one `start()` to the next) as the compact JSON text the live broadcast uses, at most `MAX_HISTORY_RECORDS` (20 000, oldest dropped and the snapshot marked `truncated`); `start()` clears it with a new `run_id` and broadcasts an empty `replay` so every client resets, and `stop()` keeps it. `concurrency_controller` bounds the in-flight work and `reorder_buffer` restores frame order before broadcast, which matters because stage assignment and the telemetry timeline are stateful. `parallel_config` holds the tuning and the FPS meter, `lifecycle.py` the start/stop helpers (resolving the ROI template, cancelling in-flight tasks), `stages.py` stateless stage helpers (timed executor runs, preview encoding, stage-failure fallbacks), `state.py` `PipelineState` and `status_payload.py` the status message.
- `api/` is the HTTP/WebSocket package. `app.py` (`create_app()`) adds GZip, the `/static` mount of `frontend/dist` and the routers. `runtime.py` creates the process singletons on import (`configure_logging()` first, then the `ConnectionManager`, the ROI templates and the `PipelineOrchestrator`), `websocket.py` holds the `/ws/telemetry` endpoint and its control-command handlers, `connections.py` `ConnectionManager`, `replay.py` the replay chunk builder and `schemas.py` the pydantic models. A new `/ws/telemetry` client first gets the Run so far as `replay` messages (`{"type":"replay","payload":{"run_id","chunk","final","truncated","records"}}`, `records` being the `telemetry` payloads, at most `REPLAY_CHUNK_SIZE` = 500 per message, `chunk` from 0, `final` on the last, one empty chunk 0 when there is no history) and only then goes live. Broadcasts made during its replay are queued for it and flushed in order afterwards (frame previews are dropped instead; a client more than `MAX_PENDING_MESSAGES` = 2 000 behind is closed with 1013), so it sees every record exactly once. Two steps rely on having no `await` in them: the history append and the routing of the broadcast, and the history snapshot and the client's registration. Only `connect()` writes to a replaying client. The REST routes are in `routes/` (`flights`, `trajectories`, `missions`, `pipeline`), one `APIRouter` each.
- `server.py` is only the uvicorn entry point (`app = create_app()`).
- The API exposes `/ws/telemetry` (WebSocket), `GET /api/status`, `POST /api/validate-url`, `GET /api/previous-flights[/{name}]`, `GET /api/trajectories[/{name}]`, and `GET /api/missions`, `GET`/`PUT /api/missions/{id}`. A mission file holds the mission, ship and booster names and the Raptor serial in each engine position of both vehicles (files saved before Super Heavy had settings read with an empty booster). The id is the mission name as a file stem, `IFT 14` -> `ift-14`, matching `results_previous/ift-14.json`; the file is `missions/engines_ift-14.json`, so a recorded flight is never written to. Filled-in missions are committed. Clients are tracked by UUID4 in `ConnectionManager`, and each session carries a correlation ID (a client-supplied UUID4 is honoured) for command tracing.

**Frontend** (`frontend/src/`): the code is in seven layers, `core → domain → api → state → ui → features → app`, and a module imports only from its own layer or any layer to its left. `src/architecture.test.ts` enforces this (type-only imports included) and finds import cycles; every module must live in a layer folder. `core/` holds the dependency-free pieces: `types.ts` (mirrors the backend message shapes, so change both sides together), `logger.ts` (leveled logging), `correlation.ts` (correlation IDs for commands), `fps-meter.ts`, the MET helpers (`met.ts`: MET parsing and formatting) and `met-clock.ts`, `app-version.ts` and the time-series and ship-track data types. `domain/` is pure logic: `engines/` (layout, detection, events, `serials.ts` with `normaliseSerial`), `overlay/` (the overlay widget ids and the URL snapshot, see below), `series-math.ts` (dedup/gap insertion, acceleration in g derived from speed; options with `derive` set are computed rather than read from the store), `flights.ts` and `downloads.ts` (the converters for the downloads below). `api/` talks to the outside: `websocket.ts` (reconnecting-websocket; one message-type check shared by the client and `parseWebSocketMessage`, and a `readOnly` option that drops every command), `status.ts`, `previous-flights.ts`, `trajectories.ts` (`/api/trajectories`), `ship-tracker-feed.ts` and `missions.ts` (the mission files). `state/` holds the stores: `StateManager` in `state-manager.ts` is the single source of truth, fed by the websocket, and also keeps every received record for download. A `replay` message (the Run's history the backend sends on connect, see the backend's `api/`) goes through the same per-record path as live `telemetry` (`ingest()`), without FPS ticks and with one notification per chunk; chunk 0 first clears the live data (time series, records, engine events, separation MET, latest record, MET clock and detector, not the pipeline status), so a reconnect never duplicates records and a new Run clears the dashboard. `time-series-store.ts`, `ship-tracker.ts`, `engine-serials.ts` (serials in localStorage), `current-mission.ts` (the mission shared by both vehicles' panels with the ship and booster, saving every change to the mission's file through `api/missions.ts`) and `flight-colors.ts`; `EngineSerials` and `FlightColors` take `{ persist: false, initial }` to live in memory only, never touching localStorage. `ui/` is the shared widgets (`popover.ts`, `color-picker.ts`, `obs-popover.ts`, `svg.ts`). `features/` has one module or folder per panel, each rendering from that state: `telemetry-display`, `met-display` (the MET alone, for its overlay), `engines/` (`visualizer.ts` and its diagram, legend and tooltip), `graphs/`, `pipeline-controls/`, `frame-preview`, `header/` and `ship-globe/`. `features/graphs/` has `index.ts` registering the Chart.js zoom and crosshair plugins and re-exporting `TimeSeriesGraphs` from `graphs.ts`, with `panels` (series options and colours), `chart-config`, `chart-data`, `toolbar`, `export/` and `plugins/` (crosshair and engine-event markers) as leaf modules. `features/ship-globe/` is the exception to rendering from state: it polls the public SpaceX tracker feed (`content.spacex.com/.../starship_tracker_public.json`) directly from the browser, keeps each `ship<N>.current` sample with altitude >= 0 as a track, and draws it on a draggable, zoomable d3-geo orthographic globe (left column; the active ship's data card is the right column) between the engines and the graphs. Recorded paths of previous ships come from `/api/trajectories` (`api/trajectories.ts`) and can be toggled on and off individually. `features/telemetry-downloads.ts` (below the pipeline controls) saves the received records as a `results_previous/`-format flight file (speed and altitude in km/h and km, before separation both vehicles get the stack reading, after it each follows the stage assignment) or as raw records, and the globe's header saves each live track as `positions_ship<N>.csv` in the `trajectories/` format. The gear on each engine diagram opens `features/engines/settings-popover.ts`, where the mission, the ship (Starship) or booster (Super Heavy, a wider panel with its 33 engines by ring) and the engine serials are entered (serials after a fixed `R`); circles keep their E-numbers and show the serial on hover, and `mission-fields.ts` offers saved missions and recorded flights matching the typed name. `app/` is the top: `main.ts` wires the modules together on the HTML shell from `layout.ts` (or mounts an overlay, below), and `styles/` holds the CSS partials that `styles/index.css` imports in order. `app-smoke.test.ts` snapshots the DOM of the whole dashboard, and `features/ship-globe/globe.trace.test.ts` hashes the globe's canvas calls (`GLOBE_TRACE_DUMP=1` dumps the full traces). Vitest runs with `isolate: false`, so tests restore what they stub, and a test that uses a module-level DOM singleton (the settings panel, colour or OBS popover) or mixes mocked and real copies of a module loads a private copy with `vi.resetModules()`.

**OBS overlays**: the OBS button on the telemetry display, on each engine diagram, on the globe and in the graphs header opens `ui/obs-popover.ts` (a singleton on `bindDismiss`/`anchorPanel`, like the colour popover), which shows the panel's overlay widgets, the URL for the selected one, a Copy button and a suggested Browser Source size. The URL is the page's own origin and path plus `?overlay=<id>&s=<snapshot>`; the ids and sizes are in `domain/overlay/widgets.ts` (`telemetry`, `met`, `engines-superheavy`, `engines-starship`, `globe` and `graph-<SeriesKey>` for each of the six series), and `domain/overlay/snapshot.ts` encodes the settings that widget uses as versioned base64url JSON with short keys (`x` compared flights with their colours, by the ids `/api/previous-flights` lists such as `ift-12`; an id not in that list is logged as a warning, `t`/`h` the globe's colour overrides and hidden paths, `m`/`e` the mission names and that vehicle's serials by engine number). Decoding validates and caps every field and never throws; a bad or missing `s` gives the defaults with a warning, and a URL stays under 2 000 characters. Each panel's `overlaySnapshot()` builds its part when the popover opens, so after changing a setting the URL has to be copied again. With such a URL `main.ts` calls `mountOverlay()` (`app/overlay.ts`) instead of building the dashboard: it adds the `overlay` class to `<html>` (`styles/overlay.css`: transparent page, no scrollbars), mounts the widget from `app/overlay-registry.ts` with `chrome: false` (no titles, buttons, selects or toolbars; the engine diagrams also drop their status legend, while a graph keeps its Chart.js legend, which tells the live flight from the compared ones, and has zoom, pan and the crosshair off; the globe is one panel: the globe on the left, drawn from the smaller side of its cell and centred in it so any source size fits, and a compact readout of the active ship in a 14rem column on the right) and connects a `StateManager` to a read-only `TelemetryWebSocket`. The backend's replay on every connect gives it the Run's history, so OBS can reload or open it late. Overlays are read-only and isolated: they never send a command, never read or write the dashboard's localStorage (settings come from the snapshot into memory-only stores, otherwise the built-in defaults), never construct `CurrentMission` (it writes mission files) and make only GET requests. Serials stay tooltip-only, and the globe overlay polls the SpaceX feed itself, so its live track starts when the overlay opens.

**Tests**: backend uses pytest with Hypothesis property tests. Frontend uses Vitest (jsdom) with fast-check, and specs sit next to the source as `*.test.ts`.

## Specs

`.kiro/specs/<feature>/{requirements,design,tasks}.md` hold the design docs for each major feature (`starship-telemetry-web-view`, `pipeline-parallelization`, `logging-improvements`, `obs-overlay`). Check the relevant `design.md` before changing the pipeline, concurrency or logging.

The specs predate the backend's package layout and still refer to flat modules such as `src/pipeline.py`, `src/server.py` or `src/logging_config.py`; that code now lives in the packages described under Architecture (e.g. `src/pipeline/`, `src/api/`, `src/core/logging_config.py`). The `RapidOCR-version` branch (EasyOCR swapped for RapidOCR) is abandoned.

# Development Guide

How to build, run and test the project, and how the code is organised.

## Overview

Real-time telemetry extraction from SpaceX Starship livestreams. A Python/FastAPI backend grabs video frames, runs OpenCV engine detection and EasyOCR text extraction, and broadcasts structured records over WebSocket to a TypeScript/Chart.js dashboard (Vite, no framework).

## Commands

Setup and launch scripts live in `scripts/windows/` (`.ps1`/`.bat`) and `scripts/unix/` (`.sh`). `setup` creates the venv and installs dependencies, and it auto-selects a CUDA or CPU torch build (override with `TORCH_CUDA`). `start` runs setup and then launches both services.

```bash
# Backend (from backend/, venv activated). Use ".[dev]" for pytest/hypothesis/httpx.
pip install -e ".[dev]"
uvicorn src.server:app --reload          # http://127.0.0.1:8000
pytest                                    # all tests (asyncio_mode=auto)
pytest tests/test_reorder_buffer.py       # one file
pytest tests/test_server.py -k name       # one test

# Frontend (from frontend/)
npm run dev                               # http://localhost:5173, proxies /ws and /api to :8000
npm run build                             # tsc && vite build (type-check gate)
npm test                                  # vitest run
npx vitest run src/core/met.test.ts       # one file
```

No linter is configured for either side. Backend imports use the `src.` package prefix (e.g. `from src.core.models import ...`), so run everything from `backend/`.

**Versioning**: `VERSION` (repo root) holds the SemVer release, `MAJOR.MINOR.PATCH`. The full version adds the commit count (`git rev-list --count HEAD`) as a fourth, build number, e.g. `0.1.0.64`. It is computed by `backend/src/core/version.py` (FastAPI) and by `frontend/vite.config.ts` at build time (`__APP_VERSION__`, shown in the dashboard header). Bump with `python scripts/bump_version.py patch|minor|major|X.Y.Z`, which also updates the copies in `frontend/package.json` and `backend/pyproject.toml`; `tests/test_version.py` fails if they drift.

`results_previous/` is tracked with Git LFS. Without `git lfs install`/`git lfs pull` it contains pointer stubs, not real data.

**Test videos**: downloaded broadcast streams live in `test_videos/<flight>/` (`output.m3u8` plus `seg_*.ts`), e.g. `ift-12/` and `ift-13/`. The folder is local-only: it is excluded through `.git/info/exclude`, not `.gitignore`, so each checkout has to fetch its own copy. The IFT-12 and IFT-13 streams are trimmed to start about 30 s before T-0. Serve one with `python scripts/serve_test_videos.py ift-12` and point the pipeline at `http://localhost:8001/output.m3u8`; without a flight argument every flight is served at `http://localhost:8001/<flight>/output.m3u8`. `--port`, `--host` and `--dir` override the defaults, and the server sends HLS MIME types and `Access-Control-Allow-Origin: *`.

## Architecture

**Backend pipeline** (`backend/src/`): `capture/` (frame extraction) → `vision/engine_analyzer` (Hough circles, colour classification against SVG-derived ROI templates) and `ocr/` (EasyOCR on defined regions) → `telemetry/stage_assignment` (attributes values to Starship or Super Heavy by separation state) → `telemetry/record_assembler` → `core/telemetry_record`, then a WebSocket broadcast from `api/`. `pipeline/` drives the stages and `api/` serves the results.

The packages are layered, lowest first: `core` → `templates` → `vision`, `ocr`, `capture` (peers) → `telemetry` → `storage` → `timeline` → `pipeline` → `api` → `server`. A module may import only from its own package or a lower layer, and peers may not import each other; `tests/test_layering.py` parses every module under `src/` (imports inside functions included) and fails on any other import. The packages' `__init__.py` files import nothing, except `capture`, `ocr` and `pipeline`, which re-export their public API (`ocr` only its result types, so it never loads torch or EasyOCR; `pipeline` lazily, on first access, so importing a submodule such as `src.pipeline.state` does not load the orchestrator either).

- `core/` holds the shared types and plumbing: `enums` (`PipelineStatus`, `SeparationState`, `OCRFieldStatus`), `models` (ROI dataclasses from SVG parsing), `gpu` (`AccelerationBackend`, `GPUCapabilities`), `telemetry_record` (`TelemetryRecord`), `version`, `paths` (`REPO_ROOT`, from which every repo directory such as `missions/`, `diagrams/` or `frontend/dist` is located) and `logging_config`/`logging_context` (human-readable, uvicorn-style logging, with the frame sequence number carried in a contextvar).
- `templates/` builds the ROI templates: `svg_parser` reads the SVGs in `diagrams/` and `template_registry` keeps them by name and loads the default. Besides the required ROIs a template may have three optional ones (a template without them still parses): `timeline_below` (x 914.5, y 936.5, 85x21 at 1920x1080), the HUD milestone arc's label spot below its line, where labels such as MAX Q, SUPER HEAVY LANDING and PAYLOAD DEPLOY pass the "now" tick (the spot above the line is `stage_sep_text`, x 914.5, y 904.5, 85x15, where LIFTOFF, STAGE SEP and SECO pass; the arc's line drifts from y ~934 early in the flight to ~926 later, which is why `timeline_below` is 21 px high); `time_sign` (x 830, y 965, 36x47), the grey `T-`/`T+` left of the HUD clock; and `countdown_time` (x 30, y 64, 202x46), the pre-launch countdown clock in the top-left corner (`T- 00:12:31` above "STARSHIP FLIGHT TEST"). All were checked on the IFT-12 and IFT-13 streams (the top-left clock on a still of the live stream, `tests/fixtures/prelaunch_clock_T-001231_topleft.png`).
- `vision/` holds `engine_analyzer` (engine status from the engine ROIs) and `gpu_detector` (`detect_gpu()`: CUDA or CPU for EasyOCR, reported in the pipeline status; torch is imported only when it runs).
- `ocr/` is the OCR package; `from src.ocr.results import OCRFieldResult, OCRResult` is what the later stages use, and the engine is imported explicitly from `src.ocr.engine`. `engine.py` (`EasyOCREngine`, `configure_torch_threads`) gates on T-0 and reads each frame's ROIs (before T-0 the countdown ROIs, when asked for, go in the gate's batch and come back with the HUD clock's read as `countdown_clock` in an otherwise unavailable result, so a clock counting down never becomes a record's MET; T-0 is still the HUD clock reading 00:00:00), using `parsing.py` (field kinds, allowlists, time/number/unit parsers, the signed countdown clock `"T- 00:12:31"` -> `"-00:12:31"` and the `T+`/`T-` sign, both read with one allowlist), `regions.py` (ROI clamping and cropping, grayscale, narrowing value boxes to their text) and `cache.py` (`FieldCache`: static ROIs such as units, stage labels and the HUD milestone label spots are reused while their pixel signature is unchanged, and re-read at least every `CACHE_REFRESH_FRAMES` frames). The rest go to `batcher.py` (`BatchedRecognizer`), one recogniser pass over the ROIs of every frame in flight. On GPU that pass is `mixed.py`, a step-for-step copy of EasyOCR's `get_text` with a per-crop allowlist mask, so it depends on EasyOCR internals (pinned `<2.0`).
- `capture/` is the frame capture package; `from src.capture import FrameExtractor, FrameExtractorConfig, SourceUnavailable` is its public API. `extractor.py` (`FrameExtractor`) runs the capture loop (open the source, read the next kept frame, dispatch it, recover a lost source) on top of two base classes: `notifier.py` (status and frame callbacks) and `connection.py` (the main capture handle: locked reads, seeking, release and reconnection with backoff). `config.py` holds the config, tuning constants and `SourceUnavailable`, `source.py` all OpenCV access and `reconnect.py` the retry with exponential backoff. A seekable file is decoded with `parallel_decoder.py` (several decoders over separate stretches, same frames as serial decoding) when `planning.py` finds the skip interval long enough to pay for the seeks; live streams are read serially.
- `telemetry/` turns one frame's results into a record: `stage_assignment` (`StageAssigner`, stateful, so it runs in video order) and `record_assembler`.
- `storage/` holds the file-backed data the API serves, all located from `core.paths`: `previous_flights` (`results_previous/`; a flight file is the plain array of records, or `{"records": [...], "timeline_status": {...}}` when the dashboard saved the mission timeline's final statuses with it, which `GET /api/previous-flights/{name}` passes through as `timeline_status`), `trajectories` (`trajectories/positions_ship<N>.csv`, below-ground rows and repeated polls dropped) and `missions` (one JSON file per mission in `missions/`).
- `timeline/` decides the live status of each mission timeline event. `status.py` (`TimelineStatusMachine`, pure, no I/O) keeps the Run's facts (the furthest MET, HUD milestone labels read, the rules' verdicts, human overrides) and derives every event's status from them: `not_yet`, `pending` (needs a person), `success`, `partial`, `failure` or `skipped` (set by a person only), each with `source` (`auto`/`human`), `evidence`, the `met` it was decided at and `updated_at`. A person's override always wins until it is cleared. Otherwise the event's `auto` decides: `manual` becomes pending at `t`, `clock` succeeds at `t`, `hud` succeeds when a matching label is read (case and space insensitive; a clipped label of at least `hud_min_match_chars` matches any part of a longer one, e.g. `SUPER HEAVY LAND` for `SUPER HEAVY LANDING`; each sighting confirms the matching event planned closest to it), and `rule` takes the verdict of its telemetry rule; `hud` and `rule` events without evidence by `t + grace_s` become pending. Its inputs are `set_timeline()` (statuses of ids that stay are kept), `on_met(met, source)` (negative before T-0; `source` is `telemetry` or `countdown`), `on_record()`, `on_hud_label(text, met)` (a label read off the HUD's milestone arc), `override()` and `reset()`; each returns a `ChangeSet`. HUD labels are matched with OCR look-alikes folded together (`0`/`Q`/`O`, `1`/`I`, `5`/`S`, `8`/`B`: "MAX 0" is MAX Q, and the evidence then names the milestone with what was read). `rules.py` (`RuleEngine`, pure) implements `TIMELINE_RULES` from each vehicle's running engine count and the ship's speed: a count must read the same in `confirm_records` consecutive visible records to be a transition (phantom detections and single misreads never are), a hidden engine panel is no evidence, and burns are followed as phases (Super Heavy ascent, MECO to 3 or 5, boostback, landing burn 13 → 5 → 3 → 0; Starship ascent, SECO, relight, landing burn 3 → 2 → 1). An unplanned drop during a burn that still completes makes it partial; failure needs explicit negative evidence (all engines off long before MECO, a relight dying within `relight_grace_s` or never lighting while the panel was on screen, a landing burn ending early, or the vehicle's data vanishing for `vehicle_lost_s` while its engines ran, which fails only the burn in progress and is withdrawn if the data returns). `samples.py` reads a record into what the rules use and checks the HUD clock against the video clock (`MetFilter`). `countdown.py` is the countdown clock before T-0 (`CountdownTracker`, pure): `clock_reading()` takes the HUD clock only while its sign reads `-` (it shows `T+` after liftoff), else the top-left clock, and the tracker turns those readings, about one a second, into a checked countdown MET: the first reading, and any far from what the video clock predicts (a misread, a recycle back up, a jump), needs `countdown_confirm_reads` agreeing readings; a visible clock showing the same value for more than `countdown_hold_s` (3 s) is a hold (the MET stops there until it changes); no clock on screen is not a hold, the MET runs on from the last reading for up to `countdown_gap_max_s` (the top-left clock leaves at about T-29 s and the HUD clock appears at about T-27 s); it never goes past 0. `config.py` holds every threshold in `TimelineConfig` (`TIMELINE_CONFIG`): `grace_s` (30 s), the debouncing, the planned engine counts (`sh_meco_counts`, `sh_planned_counts`, `ss_landing_engines`, ...), the relight and ignition windows, `ss_transonic_kmh`/`ss_subsonic_kmh` (1235/1100 km/h; real Mach 1 depends on altitude), `vehicle_lost_s`, the HUD matching limits (`hud_min_read_chars`, `hud_min_letter_ratio`: a read with fewer than 4 letters and digits, or under 75 % letters, is background noise) and the countdown's (`countdown_tolerance_s`, `countdown_confirm_reads`, `countdown_hold_s`, `countdown_gap_max_s`). `service.py` (`TimelineService`) holds the machine, the active mission and the snapshot the API sends, stamped with the `run_id` and a `revision` that keeps growing (seeded from the wall clock, so also across restarts). Its `on_hud_label()` drops reads that are noise or match no `hud` event of the timeline before they reach the machine, and `on_countdown(met, hold)` takes each countdown tick: the snapshot's `met` is then the countdown as it reads now (also after a recycle took it back; the statuses still follow the furthest MET) with `hold`, and the snapshot changes, so it is broadcast, on every tick (about once a second); once the telemetry clock runs countdown ticks are ignored.
- `pipeline/` is the orchestration package; `from src.pipeline import PipelineOrchestrator, PipelineState` is its public API. `orchestrator.py` handles Start/Stop, dispatches each captured frame (inline before T-0, as a bounded concurrent task after it) and owns the collaborators: `frame_processor.py` (`FrameProcessor`: OCR engine, ROI config, thread pools, T-0 flag, the per-frame stages and record assembly), `ordering.py` (`ReorderCoordinator`: reorder buffer, stale-gap and overflow handling, stage assignment in video order, broadcast sequence and FPS) and `broadcast.py` (`Broadcaster`: the ordered send queue and its worker, which appends each `telemetry` record to the history right before broadcasting it). The `Broadcaster` hands each sent telemetry record to the timeline (`TimelineService.on_record`) and broadcasts a `timeline_status` right after it when that changed a status. `history.py` (`TelemetryHistory`) keeps the current Run's records (a Run lasts from one `start()` to the next) as the compact JSON text the live broadcast uses, at most `MAX_HISTORY_RECORDS` (20 000, oldest dropped and the snapshot marked `truncated`); `start()` clears it with a new `run_id` and broadcasts an empty `replay` so every client resets, then resets the timeline statuses (overrides included) and broadcasts them, and `stop()` keeps both. `region_schedule.py` (`RegionSchedule`) picks each frame's ROIs as it starts processing, by its position in the video: every required ROI on every frame; before T-0 the countdown ROIs every `countdown_read_interval_s` (1 s); after it `timeline_below` every `hud_read_interval_s` (2 s; labels stay readable at the spot for 10 s or more), and `stage_sep_text` on every frame until stage separation is known (stage assignment reads it) and at the HUD rate after it, no longer dropped (both knobs in `ParallelPipelineConfig`; measured on CPU, IFT-12, 150 s: 1.42 records/s without the extra ROIs, 1.44 with them). Countdown mode: before T-0 frames are processed one at a time in video order, and each one that read the countdown ROIs goes to the orchestrator, which runs `CountdownTracker` on it and broadcasts the `timeline_status` when `TimelineService.on_countdown()` changed it. HUD milestones: as each record leaves the reorder buffer (in video order) the orchestrator keeps the label texts read with it (`stage_sep_text`, `timeline_below`) by broadcast sequence, and when the record has been sent and fed to the timeline it hands them to `TimelineService.on_hud_label()` at the MET the timeline then holds (checked against the video clock), broadcasting the statuses once if either changed them. `concurrency_controller` bounds the in-flight work and `reorder_buffer` restores frame order before broadcast, which matters because stage assignment and the telemetry timeline are stateful. `parallel_config` holds the tuning and the FPS meter, `lifecycle.py` the start/stop helpers (resolving the ROI template, cancelling in-flight tasks), `stages.py` stateless stage helpers (timed executor runs, preview encoding, stage-failure fallbacks), `state.py` `PipelineState` and `status_payload.py` the status message.
- `api/` is the HTTP/WebSocket package. `app.py` (`create_app()`) adds GZip, the `/static` mount of `frontend/dist` and the routers. `runtime.py` creates the process singletons on import (`configure_logging()` first, then the `ConnectionManager`, the ROI templates and the `PipelineOrchestrator`), `websocket.py` holds the `/ws/telemetry` endpoint and its control-command handlers, `connections.py` `ConnectionManager`, `replay.py` the replay chunk builder and `schemas.py` the pydantic models. A new `/ws/telemetry` client first gets the Run so far as `replay` messages (`{"type":"replay","payload":{"run_id","chunk","final","truncated","records"}}`, `records` being the `telemetry` payloads, at most `REPLAY_CHUNK_SIZE` = 500 per message, `chunk` from 0, `final` on the last, one empty chunk 0 when there is no history), then the latest `timeline_status` (one snapshot, taken with the history's), and only then goes live. Broadcasts made during its replay are queued for it and flushed in order afterwards (frame previews are dropped instead; a client more than `MAX_PENDING_MESSAGES` = 2 000 behind is closed with 1013), so it sees every record exactly once. Two steps rely on having no `await` in them: the history append and the routing of the broadcast, and the history snapshot and the client's registration. Only `connect()` writes to a replaying client. The REST routes are in `routes/` (`flights`, `trajectories`, `missions`, `pipeline`, `timeline`), one `APIRouter` each.
- `server.py` is only the uvicorn entry point (`app = create_app()`).
- The API exposes `/ws/telemetry` (WebSocket), `GET /api/status`, `POST /api/validate-url`, `GET /api/previous-flights[/{name}]`, `GET /api/trajectories[/{name}]`, `GET /api/missions`, `GET`/`PUT /api/missions/{id}`, and the timeline statuses: `GET /api/timeline/status` (the snapshot), `PUT /api/timeline/active` `{mission_id}` (which mission the run is, so whose timeline is followed; `null` for none, and a mission without a file has an empty timeline until it is saved; the dashboard's `CurrentMission` sends it on page load, when another mission is chosen and after saving the timeline, and saving the active mission through `PUT /api/missions/{id}` re-reads its timeline anyway; the backend keeps it in memory only) and `POST /api/timeline/{event_id}/status` `{status}` (a person's override, `null` for back to auto; 404 for an unknown event, 422 for an unknown status; overlays never call it). Every change is broadcast whole (it is small) as `{"type":"timeline_status","payload":{mission_id, run_id, revision, met, clock_source, hold, pending, events: [{event_id, status, source, evidence, met, updated_at}]}}` (`met` the furthest MET, or before T-0 the countdown clock as it reads now with `clock_source: 'countdown'` and `hold` true while it holds; sent on every countdown tick, about once a second). A mission file holds the mission, ship and booster names and the Raptor serial in each engine position of both vehicles (files saved before Super Heavy had settings read with an empty booster) and an optional `timeline` (files without one read as empty): up to 200 events `{id, t, event, vehicle, auto}`, `t` in seconds from T-0 (negative in the countdown, at most 6 hours either way), kept sorted by `t` with ties in the order given (so both T-0 rows survive), ids unique within the mission, and `auto` the source that confirms the event: `{kind: manual|clock}`, `{kind: hud, label}` or `{kind: rule, rule}` with a rule from `TIMELINE_RULES` in `storage/missions.py` (mirrored in `domain/timeline/types.ts`; the telemetry rules themselves come later). `GET /api/missions` leaves the serials and the timeline out. The id is the mission name as a file stem, `IFT 14` -> `ift-14`, matching `results_previous/ift-14.json`; the file is `missions/engines_ift-14.json`, so a recorded flight is never written to. Filled-in missions are committed. Clients are tracked by UUID4 in `ConnectionManager`, and each session carries a correlation ID (a client-supplied UUID4 is honoured) for command tracing.

**Frontend** (`frontend/src/`): the code is in seven layers, `core → domain → api → state → ui → features → app`, and a module imports only from its own layer or any layer to its left. `src/architecture.test.ts` enforces this (type-only imports included) and finds import cycles; every module must live in a layer folder. `core/` holds the dependency-free pieces: `types.ts` (mirrors the backend message shapes, so change both sides together), `logger.ts` (leveled logging), `correlation.ts` (correlation IDs for commands), `fps-meter.ts`, the MET helpers (`met.ts`: MET parsing and formatting; `parseMETToSeconds` reads `T-`/`T+`/`-`/`+` prefixes, negative before T-0) and `met-clock.ts`, `app-version.ts` and the time-series and ship-track data types. `domain/` is pure logic: `engines/` (layout, detection, events, `serials.ts` with `normaliseSerial`), `overlay/` (the overlay widget ids and the URL snapshot, see below), `series-math.ts` (dedup/gap insertion, acceleration in g derived from speed; options with `derive` set are computed rather than read from the store), `flights.ts` and `downloads.ts` (the converters for the downloads below). `api/` talks to the outside: `websocket.ts` (reconnecting-websocket; one message-type check shared by the client and `parseWebSocketMessage`, and a `readOnly` option that drops every command), `status.ts`, `previous-flights.ts`, `trajectories.ts` (`/api/trajectories`), `ship-tracker-feed.ts`, `missions.ts` (the mission files; `activate()` tells the backend the active mission) and `timeline.ts` (`fetchTimelineStatus`, `overrideTimelineStatus(eventId, status | null)`, `setActiveTimelineMission`). `state/` holds the stores: `StateManager` in `state-manager.ts` is the single source of truth, fed by the websocket, and also keeps every received record for download. A `replay` message (the Run's history the backend sends on connect, see the backend's `api/`) goes through the same per-record path as live `telemetry` (`ingest()`), without FPS ticks and with one notification per chunk; chunk 0 first clears the live data (time series, records, engine events, separation MET, latest record, MET clock and detector, not the pipeline status), so a reconnect never duplicates records and a new Run clears the dashboard. `time-series-store.ts`, `ship-tracker.ts`, `engine-serials.ts` (serials in localStorage), `current-mission.ts` (the mission shared by both vehicles' panels with the ship and booster, saving every change to the mission's file through `api/missions.ts`) and `flight-colors.ts`; `CurrentMission` also holds the mission's timeline (`timeline`, `setTimeline()`, `subscribeTimeline()`; read from the file when a mission is chosen or the page loads, and saved with every other change) and tells the backend which mission is active; `timeline-status.ts` (`TimelineStatusStore`: `snapshot`, `status(eventId)`, `pending`, `subscribe()`) holds the backend's timeline statuses, fed by `timeline_status` messages and by `load()` (the GET) on page load, and drops a snapshot whose `revision` is not newer; `mission-timeline.ts` (`MissionTimeline`: the planned events together with the status store, one `subscribe()` for either changing; the dashboard feeds the events from `CurrentMission` with `followMission()`, an overlay has no mission and reads them from the mission file the snapshot's `mission_id` names with `followStatuses()`, GET only, again whenever the mission or the set of event ids in a snapshot changes); `EngineSerials` and `FlightColors` take `{ persist: false, initial }` to live in memory only, never touching localStorage. `ui/` is the shared widgets (`popover.ts`, `color-picker.ts`, `obs-popover.ts`, `svg.ts`). `features/` has one module or folder per panel, each rendering from that state: `telemetry-display`, `met-display` (the MET alone, for its overlay), `engines/` (`visualizer.ts` and its diagram, legend and tooltip), `timeline/` (below), `graphs/`, `pipeline-controls/`, `frame-preview`, `header/` and `ship-globe/`. `features/graphs/` has `index.ts` registering the Chart.js zoom and crosshair plugins and re-exporting `TimeSeriesGraphs` from `graphs.ts`, with `panels` (series options and colours), `chart-config`, `chart-data`, `toolbar`, `export/` and `plugins/` (crosshair and engine-event markers) as leaf modules. `features/ship-globe/` is the exception to rendering from state: it polls the public SpaceX tracker feed (`content.spacex.com/.../starship_tracker_public.json`) directly from the browser, keeps each `ship<N>.current` sample with altitude >= 0 as a track, and draws it on a draggable, zoomable d3-geo orthographic globe (left column; the active ship's data card is the right column) between the engines and the graphs. Recorded paths of previous ships come from `/api/trajectories` (`api/trajectories.ts`) and can be toggled on and off individually. `features/telemetry-downloads.ts` (below the pipeline controls) saves the received records as a `results_previous/`-format flight file (speed and altitude in km/h and km, before separation both vehicles get the stack reading, after it each follows the stage assignment; with timeline statuses the file is `{"records", "timeline_status"}`, the final snapshot with sources and evidence, never engine events) or as raw records, and the globe's header saves each live track as `positions_ship<N>.csv` in the `trajectories/` format. The gear on each engine diagram opens `features/engines/settings-popover.ts`, where the mission, the ship (Starship) or booster (Super Heavy, a wider panel with its 33 engines by ring) and the engine serials are entered (serials after a fixed `R`); circles keep their E-numbers and show the serial on hover, and `mission-fields.ts` offers saved missions and recorded flights matching the typed name. The Timeline button under the mission fields opens `features/engines/timeline-editor.ts` in its place: the Countdown and Flight test tables of SpaceX's mission page are pasted into two boxes and parsed live by `domain/timeline/` (`parse.ts`: rows `HH:MM:SS`/`MM:SS` with an optional `T-`/`T+`, the box deciding the sign, headers skipped and every other unreadable line returned as a warning; `guess.ts`: the keyword table that guesses each row's vehicle and automation source), then edited row by row in a preview table and saved through `CurrentMission`. A pasted row with the same time and text as an event of the saved timeline keeps its id (`buildTimeline(drafts, existing)`), so the backend's statuses and overrides, kept by id, survive pasting the tables again. The timeline needs a named mission and is not offered in overlays. `features/timeline/timeline-panel.ts` (`TimelinePanel`) is the live panel, a full-width section between the engines and the globe (`#mission-timeline`; the list scrolls inside the panel, 18 rem high): every event in order with a status circle, its time (`formatTimelineTime`), text and a vehicle tag (`SH`, `SS`, `ALL`); past events are not dimmed. The current event (the last one at or before the MET, the second of two at T-0) is highlighted, and the header shows the MET, `next: <event> in m:ss` and how many events wait for a person. The MET is the later of the latest record's and the snapshot's `met` (so a countdown before liftoff, with `clock_source: 'countdown'`, shows `T-`, followed by `HOLD` while the snapshot says it holds; `—` while neither is known). The list follows the current event unless the user wheeled, touched, pressed or typed in it within the last 10 s (`AUTO_SCROLL_PAUSE_MS`). The circles (`status-circle.ts`, SVG; each status differs in shape as well as colour, so none relies on colour alone): not yet = hollow grey ring, pending = amber ring with a dot that pulses slowly (off under `prefers-reduced-motion`), success = filled green with a check, partial = ring with its left half filled (yellow-green), failure = filled red with a cross, skipped = grey dashed ring with a slash; a small `H` badge marks a person's override, and the tooltip gives the status, who set it, the evidence and the MET it was decided at. Clicking a circle opens `override-menu.ts` (a singleton `role="menu"` popover: the six statuses as `menuitemradio`, "Back to auto" while the source is `human`; arrows, Home, End, Enter, Space, Escape, focus back to the circle) which calls `overrideTimelineStatus`; the row only shows a brief saving state, the circle changes with the snapshot that comes back (also applied from the response, an older revision being ignored), and a failure shows an inline `role="alert"` line. `domain/timeline/view.ts` holds the pure part: labels, colours, current and next event, the clock and countdown text, and which events a vehicle's graphs show. On the graphs, events from T+0 on are dashed lines (thin, finely dashed, no shape) in their status colour, drawn by the engine-events plugin with the engine markers (`timeline-markers.ts` builds them, `kind: 'timeline'`) and, like them, included in the PNG export and without a toggle; the label is the hover tooltip only (time and text, status and who set it, evidence). Vehicle rule: Super Heavy graphs show the Super Heavy and shared (`both`) events; Starship graphs show the Super Heavy and shared events before the stage separation and the Starship and shared ones from then on, all of them while separation is unknown. `app/` is the top: `main.ts` wires the modules together on the HTML shell from `layout.ts` (or mounts an overlay, below), and `styles/` holds the CSS partials that `styles/index.css` imports in order. `app-smoke.test.ts` snapshots the DOM of the whole dashboard, and `features/ship-globe/globe.trace.test.ts` hashes the globe's canvas calls (`GLOBE_TRACE_DUMP=1` dumps the full traces). Vitest runs with `isolate: false`, so tests restore what they stub, and a test that uses a module-level DOM singleton (the settings panel, colour or OBS popover) or mixes mocked and real copies of a module loads a private copy with `vi.resetModules()`.

**OBS overlays**: the OBS button on the telemetry display, on each engine diagram, on the globe and in the graphs header opens `ui/obs-popover.ts` (a singleton on `bindDismiss`/`anchorPanel`, like the colour popover), which shows the panel's overlay widgets, the URL for the selected one, a Copy button and a suggested Browser Source size. The URL is the page's own origin and path plus `?overlay=<id>&s=<snapshot>`; the ids and sizes are in `domain/overlay/widgets.ts` (`telemetry`, `met`, `engines-superheavy`, `engines-starship`, `globe`, `timeline`, `timeline-next` and `graph-<SeriesKey>` for each of the six series), and `domain/overlay/snapshot.ts` encodes the settings that widget uses as versioned base64url JSON with short keys (`x` compared flights with their colours, by the ids `/api/previous-flights` lists such as `ift-12`; an id not in that list is logged as a warning, `t`/`h` the globe's colour overrides and hidden paths, `m`/`e` the mission names and that vehicle's serials by engine number). Decoding validates and caps every field and never throws; a bad or missing `s` gives the defaults with a warning, and a URL stays under 2 000 characters. Each panel's `overlaySnapshot()` builds its part when the popover opens, so after changing a setting the URL has to be copied again. With such a URL `main.ts` calls `mountOverlay()` (`app/overlay.ts`) instead of building the dashboard: it adds the `overlay` class to `<html>` (`styles/overlay.css`: transparent page, no scrollbars), mounts the widget from `app/overlay-registry.ts` with `chrome: false` (no titles, buttons, selects or toolbars; the engine diagrams also drop their status legend, while a graph keeps its Chart.js legend, which tells the live flight from the compared ones, and has zoom, pan and the crosshair off; the globe is one panel: the globe on the left, drawn from the smaller side of its cell and centred in it so any source size fits, and a compact readout of the active ship in a 14rem column on the right) and connects a `StateManager` to a read-only `TelemetryWebSocket`. The backend's replay on every connect gives it the Run's history, so OBS can reload or open it late. Overlays are read-only and isolated: they never send a command, never read or write the dashboard's localStorage (settings come from the snapshot into memory-only stores, otherwise the built-in defaults), never construct `CurrentMission` (it writes mission files) and make only GET requests. The timeline overlays (`?overlay=timeline`, the full list, 460x600; `?overlay=timeline-next`, a ticker with the current event and the next one with its `in m:ss`, 460x110; both offered by the OBS button on the timeline panel, and neither takes snapshot settings, so the URL is just `?overlay=timeline&s=<empty snapshot>`) and the graph overlays load the timeline: `mountOverlay()` gives them a `MissionTimeline` whose status store takes the `timeline_status` messages of the same socket and one `GET /api/timeline/status` on load, and which reads the planned events with `GET /api/missions/<mission_id>` for the `mission_id` the snapshot names (the timeline is too big for the URL, and the active mission is the backend's to know, so the URL never has to be copied again when the mission changes). They render the panel with `chrome: false`: circles are spans, so there is no menu and no button, and the other widgets load nothing of the timeline. Serials stay tooltip-only, and the globe overlay polls the SpaceX feed itself, so its live track starts when the overlay opens.

**Headless runs**: `python -m tools.headless_run <url> --seconds 60` (from `backend/`) drives the real pipeline without the server and evaluates the output (throughput, clock, field availability, dropped frames); `--timeline <mission file>` follows that file's timeline and reports each event's final status and the countdown ticks (every `timeline_status` message goes to `timeline.jsonl`).

**Tests**: backend uses pytest with Hypothesis property tests. Frontend uses Vitest (jsdom) with fast-check, and specs sit next to the source as `*.test.ts`.

## Specs

`.kiro/specs/<feature>/{requirements,design,tasks}.md` hold the design docs for each major feature (`starship-telemetry-web-view`, `pipeline-parallelization`, `logging-improvements`, `obs-overlay`). Check the relevant `design.md` before changing the pipeline, concurrency or logging.

The specs predate the backend's package layout and still refer to flat modules such as `src/pipeline.py`, `src/server.py` or `src/logging_config.py`; that code now lives in the packages described under Architecture (e.g. `src/pipeline/`, `src/api/`, `src/core/logging_config.py`). The `RapidOCR-version` branch (EasyOCR swapped for RapidOCR) is abandoned.
